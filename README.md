# T1 test task: PostgreSQL 18 + .NET 10

A partitioned operations table **T1**, data generated by a stored procedure, a globally unique operation guid,
two scheduled jobs (every 5 s and every 3 s), a materialized view with running totals and logical replication
of T1 to a second PostgreSQL instance.

| Container | Role |
|---|---|
| `pg-primary` | PostgreSQL 18: T1 and all SQL logic, `wal_level=logical`, publication `t1_pub` |
| `pg-replica` | a separate PostgreSQL 18 instance: subscription `t1_sub`, copy of T1 with the same partitions |
| `t1-service` | .NET 10 (ASP.NET Core + Quartz.NET 4): migrations, seeding, replication setup, scheduled jobs, HTTP API |

## Quick start

Only Docker is required (a local .NET SDK is optional). Settings live in `.env`, which is not committed:
create it from [`.env.example`](.env.example) (`make up` does this automatically).

```bash
cp .env.example .env
docker compose up -d --build
docker compose logs -f t1-service
```

On the first start the service migrates the primary, generates 120 000 rows (`CALL t1_generate_data()`, ~2 s)
and starts the jobs; in the background it migrates the replica, mirrors the partitions and creates the subscription:

```
add-operation: id=120003 state=0 amount=6606.89 client=392 offline guid=01a1cf98-...
confirm-operations: second=12 -> even ids, confirmed 0
add-operation: id=120004 state=0 amount=2577.57 client=44 online guid=01a1cf98-...
confirm-operations: second=15 -> odd ids, confirmed 1
```

### 1. Table T1

| Field | Column | Type |
|---|---|---|
| date | `op_date` | `timestamptz`, partition key |
| id | `id` | `bigint` identity |
| amount | `amount` | `numeric(18,2)`, `> 0` |
| state | `state` | `smallint`: 0 new, 1 confirmed |
| operation guid | `operation_guid` | `uuid` (UUIDv7) |
| message | `message` | `jsonb`: `{"account_number": "UA…", "client_id": 42, "operation_type": "online"}` |

* Monthly partitions `t1_YYYY_MM` with UTC boundaries, created by the idempotent `t1_ensure_partitions(from, to)`
  (`CREATE TABLE` + `ATTACH PARTITION`, so readers and writers of T1 are not blocked).
* The service keeps 2 months ahead on both instances and mirrors every partition of the primary on the replica, every minute.
* PK `(id, op_date)` (a partitioned PK must contain the partition key); `CHECK`s validate `amount` and `message`.

### 2. Data generation

```sql
CALL t1_generate_data();   -- 120 000 rows from the 1st day of month M-3 (UTC) to now(): 4 calendar months
CALL t1_generate_data(p_rows => 200000, p_from => '2026-07-01 00:00+00', p_to => '2026-11-01 00:00+00');
```

A procedure because it commits per batch (`p_commit => false` makes it atomic inside a transaction; the service seeds
that way, so an interrupted seed leaves nothing behind). Rows are spread evenly over the period and inserted
chronologically; the result does not depend on the session time zone. Guids are UUIDv7 carrying `op_date`,
account numbers are valid UA IBANs; ~1 % of rows are generated pending, the job confirms them right after start.
Only the owner may run it.

### 3. Unique operation guid

PostgreSQL has no global indexes on partitioned tables: `UNIQUE (operation_guid)` is rejected, and
`UNIQUE (operation_guid, op_date)` would allow the same guid on another date. So uniqueness is enforced by a
non-partitioned registry `t1_operation_guid (operation_guid PRIMARY KEY, t1_id, op_date)` kept in sync by row
triggers in the same transaction:

* insert (also `COPY`, `MERGE`, upserts, straight into a partition): registers the guid; a duplicate fails with
  `23505` (HTTP 409; a SERIALIZABLE transaction may get `40001` instead);
* changing the guid re-keys the registry entry; `id` and `op_date` are immutable;
* delete releases the guid, `TRUNCATE t1` clears the registry.

Concurrent inserts of one guid serialize on the registry's primary key. The trigger functions are `SECURITY DEFINER`
and not executable by other roles. DDL bypasses row triggers: after dropping, detaching or attaching a partition
run `SELECT * FROM t1_operation_guid_resync()` (a detached month is reported, not silently re-created). Superusers can
bypass any trigger, which is the usual limit of this approach.

### 4–5. Scheduled jobs

Quartz.NET jobs in the service (the task asked for the .NET stack), UTC cron from `.env`:

* `0/5 * * * * ?` → `SELECT * FROM t1_add_operation()`: a random operation with `state = 0`;
* `0/3 * * * * ?` → `SELECT * FROM t1_confirm_operations()`: `state = 1` for pending rows whose `id % 2` equals
  the current second `% 2` (database clock).

The 3-second job fires at seconds 0, 3, …, 57, so the parity alternates, also across minutes (57 → 00), and every
new row is confirmed within 6 s. The second is read after the table lock is granted, and rows locked by other
transactions are skipped (`SKIP LOCKED`) rather than waited for.

* A tick that comes while the previous run is busy, or more than 1 s late, is skipped; a transient database error
  (e.g. a restart) is retried once.
* With several service instances only one runs the jobs: the holder of an advisory lock on the primary. Every run
  re-checks the lock (and takes it right away after a primary restart); the server drops a vanished leader's session
  within seconds (TCP keepalive), so another instance takes over.
* The operation of a tick gets a guid derived from the tick, so a retry or a second leader cannot insert it twice.

### 6. Materialized view

```sql
CREATE MATERIALIZED VIEW t1_client_totals AS
SELECT (message ->> 'client_id')::bigint AS client_id, message ->> 'operation_type' AS operation_type,
       sum(amount) AS total_amount, count(*) AS operations_count
  FROM t1 WHERE state = 1 GROUP BY 1, 2;
```

The totals cover confirmed operations, which is what changes on 0 → 1. A row trigger marks the transaction on every
0 → 1 update (job, API, manual, directly on a partition), and a deferred constraint trigger refreshes the view once
at commit:

* visible atomically with the confirmed rows; nothing happens on rollback;
* `REFRESH ... CONCURRENTLY` never blocks readers;
* refreshes are serialized by an advisory lock taken before the refresh starts, so a refresh always sees previously
  committed confirmations. Refresh manually only with `SELECT t1_refresh_client_totals()` (the generator does too);
* confirmations must run in READ COMMITTED (the default); other isolation levels get a clear error;
* only 0 → 1 refreshes the view (the requirement); after other changes (1 → 0, deletes) call `t1_refresh_client_totals()`.

Each refresh recomputes the aggregate (tens of ms here). For much larger volumes a totals table updated
incrementally by the same trigger would be cheaper.

### 7. Replication

Logical replication, because it replicates a table rather than the whole cluster:

```sql
-- primary
CREATE PUBLICATION t1_pub FOR TABLE t1 WITH (publish_via_partition_root = true);
CREATE ROLE replicator WITH LOGIN REPLICATION PASSWORD '...';
GRANT SELECT ON t1 TO replicator;
-- replica (same t1 schema and partitions)
CREATE SUBSCRIPTION t1_sub
    CONNECTION 'host=pg-primary port=5432 dbname=t1db user=replicator password=...'
    PUBLICATION t1_pub WITH (copy_data = true);
```

The service sets this up in the background (the jobs on the primary do not wait for the replica) and repeats the
whole idempotent setup every minute, so it rebuilds a re-created replica and repairs a subscription whose slot is
missing or lost, a failing initial copy, an orphaned slot, changed credentials or a renamed subscription.
Partitions created directly on the primary (e.g. a manual `CALL t1_generate_data(...)` for another period) reach the
replica within 10 s; until then the subscription waits. Status: `GET /api/replication`.

Notes: DDL is not replicated. `TRUNCATE`/`DROP` of a single partition (retention) must be done on both instances,
or old rows removed with `DELETE`. `max_slot_wal_keep_size` (`.env`) bounds the WAL kept for a stalled replica;
beyond it the service re-copies T1.

## Manual checks

```sql
-- primary
\d+ t1
SELECT tableoid::regclass, count(*), min(op_date), max(op_date) FROM t1 GROUP BY 1 ORDER BY 1;
SELECT id, op_date, state FROM t1 ORDER BY id DESC LIMIT 5;    -- run again: state goes 0 -> 1
SELECT * FROM t1_add_operation(p_operation_guid => (SELECT operation_guid FROM t1 LIMIT 1));  -- 23505
SELECT * FROM t1_client_totals WHERE client_id = 42;
-- replica
SELECT count(*), max(id), sum(amount) FROM t1;
SELECT subname, received_lsn, last_msg_receipt_time FROM pg_stat_subscription;
```

## Alternative: pg_cron

The jobs can also live in the database. pg_cron is not packaged for the Alpine image, so the primary would be built
from `postgres:18` with `apt-get install postgresql-18-cron`, `shared_preload_libraries = 'pg_cron'`,
`cron.database_name = 't1db'`. Then, on the primary (with `JOB_ADD_OPERATION_ENABLED=false` and `JOB_CONFIRM_OPERATIONS_ENABLED=false` in `.env`):

```sql
CREATE EXTENSION pg_cron;
SELECT cron.schedule('t1-add-operation',      '5 seconds', 'SELECT t1_add_operation()');
SELECT cron.schedule('t1-confirm-operations', '3 seconds', 'SELECT t1_confirm_operations()');
SELECT cron.schedule('t1-cron-history', '0 * * * *', $$DELETE FROM cron.job_run_details WHERE end_time < now() - interval '1 day'$$);
```

Caveats, verified on PostgreSQL 18 + pg_cron 1.6: interval schedules are not aligned to wall-clock seconds and
drift by a few ms per run, so two consecutive runs occasionally share a parity; six-field (seconds) cron expressions
are silently read as minutes; partitions still have to be created ahead on both instances.

## Tests

90 integration tests (xunit v3 + Testcontainers): two PostgreSQL 18 containers on a private network; tests create
their own databases on them. The end-to-end tests run the real service, including a replica wiped while it runs.

```bash
make test                         # no local .NET SDK needed (NuGet cache in the docker volume t1-nuget)
dotnet test --solution T1.sln     # with a local .NET 10 SDK
```
